# Security

Runbooks exists so that an agent can prepare work on your servers without being able to do it. This page says how that is enforced.

## Agents propose, people run

- The agent routes (`/plugin-api/runbooks/agent/...`) can list hosts, write runbooks and steps, change steps that have not run, and read. There is no agent route that runs, sends, skips or reopens a step, or writes a note.
- An agent can end only its own steps (`owner: "agent"`), with `POST /agent/steps/{id}/complete`, once every earlier step ended. Termix runs nothing for such a step: Run and Send to terminal refuse it, and its command is only text. A person can skip or reopen it. The completion is audited with the token's name.
- Those actions are person routes (`/plugin-api/runbooks/...`). Termix checks the login, the route checks the Use Runbooks permission, and a request without a signed-in user is refused.
- A request made with a Termix API key (`tmx_...`) is refused on every route that acts: running, stopping, sending to a terminal, marking a run done or failed, skipping, reopening, notes, hiding output, runbook status and tokens. Reading is allowed. Approving a command takes a person in the Termix UI.

## Tokens

- The agent routes are declared public to Termix, so Termix does no login check for them; it records the declaration in its audit log and logs each request. Runbooks then requires `Authorization: Bearer rbk_...` on every request.
- A token is 32 random bytes. Only its SHA-256 is stored. A check compares the hash against every live token in constant time.
- Revoked tokens are refused. A token stops working when its creator loses the Use Runbooks permission.
- Each token may make 120 requests a minute; Termix also limits each address on the public routes.
- A token may name only the hosts ticked for it. The person making or editing the token picks them from the SSH hosts they see, and each one is checked for their connect access and for SSH being switched on. The token keeps a copy of each host's id, name, address and folder and that it takes SSH, and (1.4.7) what HAW VM Manager said about the host when it was saved (see [VM steps](#vm-steps)), nothing else. The token sees only runbooks made with its creator's tokens.
- The host list limits what an agent may propose. Running is separate: the person who runs a step needs connect access to its host at that moment.

## What runs is what you saw

- The page shows each step's resolved command and a hash of the host id, that command and, for a step with standard input, where the input comes from; when a check uses a value (1.4.6), the hash covers the checks with their values too. Running sends back the step's revision and that hash. If the agent changed the step, or a value changed, the hashes differ and the run is refused.
- **Run** runs a step only after a confirm that shows the host and the exact command. The command runs on its own SSH connection, opened through Termix as the person who pressed Run: Termix checks their access to the host, uses its stored login and checks its host key, as for any connection. The request answers at once and the command goes on in the background as that person.
- **Sequences** (1.4.10). A sequence step's hash covers the host, the workdir and every item: each run item's command with its values, its checks, its `onFail`, and each delay's seconds and reason. The Run confirm lists every item. One Run runs the items in order as the person who pressed it, each run item on its own connection through core's connect pipeline, and each is audited. Core keeps the acting person for the timers and promises that follow the request, but checks no session after it, so before each item after the first Runbooks asks core whether that person may still connect to the host (`ctx.hosts.checkAccess`), and stops the sequence if not. A person who signs out does not stop a sequence that runs; Stop does.
  - **Values flow forward without a new confirm.** A value an item captures fills `{{name}}` in later items of the same run. The confirm shows such a name as written, with a line that an earlier item fills it, and the item's record keeps the command as it ran. As everywhere in Runbooks, a value goes into a command as plain text, without shell quoting: a value the host prints can change what a later item runs. Capture only values whose form you control, or check them with a `value` check (`matches`) on the capturing item, which fails the item before a later one reads the value.
  - **Continue from item N** is a new run that carries the records of the items that passed (they do not run again) and runs the rest. It is refused when the sequence's hash changed since that run (the step or a value it uses changed), when the latest run did not fail, and for a person who may not connect; it skips the repeat question only, not the order, wait or rule questions. **Run** again from item 1 asks the repeat question.
  - A **delay** item is a timer in Runbooks; nothing runs on the host. **Skip** ends it early and is audited. A Termix restart ends the run as interrupted: the item that ran is marked failed, the items after it stay waiting, and the person continues.
  - A **wait** item, and a run item with **retry**, run their command again on a schedule (1.4.10, phase 2). One Run press is the person's consent for every attempt of it: attempts do not ask the repeat question, and the confirm shows the schedule ("up to 120 attempts, every 30 s, at most 1 h"), which is part of the hash the person approves. The server runs the attempts after the answer, also with the page closed, as the person who pressed Run; before each attempt after the first, Runbooks asks core again whether that person may still connect to the host, and stops the item and the sequence if not (whatever the item's `onFail`). Each attempt opens its own connection through core's connect pipeline. Limits per item, whatever the author writes: 500 attempts and 2 hours in all; an attempt's time limit is cut to the time the item has left, so a hung attempt fails at its limit and cannot hold the item past it. **Try now** (start the next attempt before its delay ends) and **Stop** are person routes, refused for agents and API keys; Try now is audited, and so is each item's end with its attempt count (one audit line per item, not per attempt). A Termix restart fails the waiting item and its running attempt as interrupted; the person continues from that item, and its wait starts again at attempt 1.
  - `workdir` runs each command as `cd -- '<workdir>' && <command>`, the folder in single quotes with each quote escaped, so the folder name cannot add a command.
- **No sleep in commands** (1.4.10). Runbooks refuses, when a step is written, a command that waits a fixed time (`sleep`, `Start-Sleep`, `timeout /t`, `ping -n` to the host itself), and points to the `delay` item, so the person sees what a step waits for. It is a rule on what agents write, not a sandbox: a script the command calls may still wait. An admin setting turns it off (on by default); steps stored before keep running.
- **Stop** is a person route like Run, refused for agents and Termix API keys, and audited. On a sequence it ends the item that runs, and the rest do not run.
- **Send to terminal** asks no such question: it types the command into a terminal to the step's host without pressing Enter, so nothing runs until the person reads it there and presses Enter. The run is recorded only once that terminal is connected.
- Run and Send to terminal refuse a host that does not take SSH.
- A repeat (the step ran before, or the same command ran on the same host in the last 24 hours), a run out of order and a start before a step's wait timer ended each need their own confirm. A start before the wait ended is audited, and the run keeps how many seconds were left.
- A step with no command is marked **Done** or **Failed** by a person only (a person route, refused for agents and Termix API keys), and the run records who and when.
- **Mark done** on a terminal run needs pasted output; the server refuses an empty paste.
- **Output read from the terminal** (1.4.9). After Send to terminal, the page reads the terminal it typed into, in the person's browser, and fills the Mark done box with the command's output. Nothing is saved until the person presses Mark done or Mark failed, and they see, and can change, all that will be saved. The text goes to the server as the pasted output, so it gets the same secret masking as a paste or a Run: secrets the step reads or captures, and those earlier secret steps made, become `[secret:<name>]`, and a hidden step's output reads `[hidden by owner]` for agents. The run's `outputSource` says that the page read it from the terminal, and whether the person changed it. It is what the page reports, not proof: any client can send it. Agents read `null` for it on a hidden step, since whether the command printed anything, and whether the person changed it, is that step's output too.
  - Text typed at a prompt that does not echo (`sudo`, `read -s`, `Read-Host -AsSecureString`) never reaches the screen, so it is never read. `Read-Host -AsSecureString` shows one `*` per character: the length shows, never the text.
  - Text the terminal does show (a plain `read`, a token the command prints, something typed at a prompt that echoes) is read like any output. Runbooks cannot replace it unless it is a secret the step knows, because it never passes through Runbooks. Check the box before Mark done, and use a Run with hidden typed input for prompts where you can.
  - It follows the terminal's output from the moment it types the command, and stops reading at the first line after the output that looks like a prompt, so commands typed after it are never read. It starts only when the terminal's last line looks like a prompt (not a tmux status line or a message still printing). When it cannot find the command's line or a prompt for sure, the box says to check the start or the end, and never says the command looks finished. It reads only the terminal the page typed into, only in that browser, and only until Mark done or Mark failed, the run ending on another device, a new Send to terminal on that terminal, or its tab closing; a reload ends it.
  - **Mark failed** sends the text read from the terminal only if the person opened (clicked or tapped into) or changed the box; otherwise it sends no output, as before 1.4.9.
- A step that has run cannot be changed or removed by the agent, and nothing can be inserted before it. Runs are never deleted.

## Host keys

When Termix connects to a host with no person to ask and the host has no stored host key, it accepts whatever key the server shows. So **Run** first reads the host and refuses one without a stored key fingerprint, with "open a Terminal to this host once to store its host key". **Send to terminal** is not refused: the terminal asks you about the key itself.

## Hidden output

For a step marked hidden, agents get `[hidden by owner]` instead of its standard output, standard error, pasted output and captured values. Captured values of four characters or more are also masked where they appear in other steps' output and captures, except a value from a small fixed set (a VM step's `state`, a Decision's option id): whether `running` is masked would tell which state it is (BUG-016), so the steps that read such a value are hidden instead (below). An agent can mark a step hidden but cannot clear the mark. Check results stay visible on a hidden step: they say whether each check passed, never the output, but a check such as `contains` does tell whether the output had that text. A failed check on a hidden step says only that it failed, not why (a value not captured, a pattern that took too long).

**The agent view is built, not masked** (BUG-011). Masking text after the fact leaks: any text that equals a hidden value comes back masked, so an agent that writes a guess learns whether it was right. So what agents read is made from parts that never held a hidden value:

- A run's command and its check words are filled in again from the step's command and checks, with the values agents saw when the run started (hidden ones as `[hidden by owner]`). A literal an agent wrote into a command or a check stays as written.
- Text an agent wrote is never masked: its own step's output and command. A Decision step's choice and value are the author's option ids, and are never masked either.
- An agent step's checks are tested with the values agents see, so `contains {{tok}}` on an agent step tests for `[hidden by owner]`, never the hidden value. Such a check is refused when the step is written (400 on create, add, change and amend).
- A step whose standard input is a hidden step's output, or a value that a hidden step captures, counts as hidden: its output and captures read `[hidden by owner]`, and so on for a step that reads its output in turn. A hidden step's run, and a run that read a secret, show no input size.
- A step whose command, checks or standard input reads a hidden value from a small fixed set (a hidden VM step's `{{build.state}}`), or whose standard input is a hidden VM or Decision step's output, counts as hidden too (BUG-016), and every value it captures counts as such a value in turn: it may be the state again. An agent step is not hidden this way; its checks read the values agents see.
- A hidden step that ended done shows each capture it declares as `[hidden by owner]`, whether the pattern matched or not, in its run, in `effectiveValues` and in a later step's `missing`. It shows `truncated: false` and no `lastOutputAt`.
- A sequence step's items (1.4.10) are hidden as its runs are: each item's output, captures, error and size read `[hidden by owner]` or nothing on a hidden step, a passed item shows each capture it declares as `[hidden by owner]`, and each run item's command and check words are built again from the item as written, with the values agents saw and the earlier items' captures as agents read them. A sequence whose run item reads a hidden fixed-set value counts as hidden, as a one-command step does. Its status, exit code, the time each item took, and whether each check passed stay visible, as for a run.
- A wait's or a retried item's attempts (1.4.10, phase 2) are hidden as their item is: on a hidden step each attempt's output and error read `[hidden by owner]` or nothing, and it shows no size (`truncated: false`); captures come only from the attempt that passed, and read `[hidden by owner]`. **What stays visible on a hidden step, on purpose:** how many attempts ran, the time of each, its exit code, whether each check passed and each `stopIf` check matched, why it did not pass (`exit`, `check`, `timeout`, `connect`, `stop-if`), and when the next attempt starts. This is no new oracle: an agent wrote the checks, and the item's status, exit code and check results were visible already, so the count only tells on which attempt the agent's own checks passed. A hidden value can still change the count if the agent writes a check that reads it, as it can change a run's pass or fail today; a check that reads a hidden value is refused when written, as before. The hidden-data tests (G15 to G15c in `tests/backend/hidden-agent-view.test.ts`) prove that two runbooks that differ only in a hidden value read the same to agents, while a wait waits and after it ends.
- Captures read the output with secrets hidden, as checks do, so a capture never takes part of a secret or of hidden typed input.
- A run's `error` is built from its parts (BUG-014). A hidden step's failed run says only `[hidden by owner]`, and its run that ended done has no error: a capture pattern that took too long, or a secret capture with no match, depends on its output. On a visible step, Termix's own words are masked and the capture and secret names the author wrote stay as written.

The test suite checks this: each test in `tests/backend/hidden-agent-view.test.ts` builds a runbook twice with two hidden values and compares all that an agent can read, through REST, MCP, events, the list and webhooks.

**What stays possible.** A visible step that a person runs can print a hidden value, and Runbooks masks it only where it finds the value as it is. Runbooks cannot see it in a changed form (reversed, base64, its length, part of it), so such a form reaches agents. A value shorter than four characters is not masked at all, and typed input shorter than four characters is not hidden for anyone. The same holds for an agent's guess written into such a command: if the command prints the guess and it equals a hidden value, the output shows it masked. A visible step's standard input that holds a masked value still shows its size. Each of these needs a person to run the step, and the person sees the command in full in the Run confirm. No route gives an agent a hidden value, or tests a guess of one, without a person. To keep such a step's output from agents, hide the step too.

A hidden step's own results stay visible to agents, since later steps and rules depend on them: its status, its exit code, whether each check passed, how long it ran, and whether its secret captures matched (a secret capture with no match fails the step). Each of these says something about the hidden output, and each needs a person to run the step. The Run confirm shows that person the command, the checks, and the pattern of each capture and secret capture before the step runs.

A `when` rule (1.4.6) is a question an agent can ask again and again without a person: it writes or changes the rule, and sees the answer in `condition.state`, `nextStepId`, the progress, `agent-turn` and the 409 `not-needed` of its own routes. So **a rule cannot read hidden output** (BUG-010). Every rule, whoever wrote it and by whatever route, is worked out each time on what the agent view shows: the output of a hidden step reads `[hidden by owner]`, values that hidden steps captured read `[hidden by owner]`, those values are masked in other steps' output and captures as the agent view masks them, and `{{name}}` in an output rule is filled with the masked value. A rule's state then depends only on what agents can already read, so no rule, and no later change to a step or to the hide mark, tells an agent anything about hidden data. The test suite checks this: two runbooks that differ only in hidden output and values give the same answer in every field an agent reads (`tests/backend/conditions-agent-data.test.ts`).

The cost is that a rule cannot test hidden output. To branch on it, give the hidden step a check (a check reads the real output, once, when the person runs the step, and the person approves it with the command) and give the later step a status rule, `{ "step": 1, "status": "failed" }`. On the page, a rule that reads hidden output shows "This rule can't see hidden output". The exit code is not hidden, so an `exitCode` rule written before the step was hidden still works. Values shorter than four characters are not masked in other text, for agents or for rules; since BUG-011 only a step a person runs can put one in front of an agent. Agent routes still refuse a rule that reads a hidden step's output or values (400), and a change that would make one (409 `when`), as an early error; the security does not depend on it. The words of a rule carry filled values, so agents get them masked like check results.

A Decision step cannot be hidden from agents (400): its options and the choice are the author's own text.

## Secrets

Runbooks keeps no secret of its own. Secrets go through the OpenBao Secrets plugin's service, `openbao-secrets.store`, which Runbooks declares as an optional requirement: without it, steps that capture or read a secret are refused, and nothing falls back to another store.

- **Where they live.** A captured secret is stored in OpenBao, in Runbooks' own area of OpenBao Secrets, at `runbooks/<runbook id>/<name>`, with an expiry 7 days ahead. Runbooks reaches its area with a key that OpenBao Secrets hands to a receiver only Runbooks can register; Runbooks keeps the key in memory and takes one only while its own request for it runs. Library secrets (`mine/`, `shared/`) stay where the person put them.
- **Who.** Every call runs as the person who presses Run or Mark done, and OpenBao Secrets checks their **Use secrets** permission first; a library secret is read with their own access to it. Anyone with Use Runbooks and Use secrets who runs a step of the runbook reaches its captured secrets, as they do its output.
- **Never kept, never shown.** A secret is never written to Runbooks' tables, never sent to the browser, never given to agents, and never part of a command (there is no secret placeholder). The runs table keeps only the names of the secrets a run read or stored, and the source of its standard input with its size.
- **Redaction.** Before any output is stored or shown (the run row, the live output, the API, MCP and the audit log), every secret value a step captured or read is replaced by `[secret:<name>]` in standard output, standard error, pasted output and captured values. Output arrives in pieces, so Runbooks holds back the last characters of each stream (one fewer than the longest value) until more arrives: a value split across two pieces is still replaced. The output of a step that captures a secret is not shown or saved until the run ends, because the value is known only then. Redaction finds the exact text only: a command that prints a secret changed (encoded, split by other text) prints it where it can be read, so write commands that read secrets from standard input and do not print them.
- **Checks.** A step's checks are tested on the output after redaction, and on captured values after redaction (1.4.1). An agent writes checks, so a check on the real value would pass or fail on the secret's characters and tell the agent about them one guess at a time; on the redacted text it cannot.
- **What agents see.** Agents can set `stdin` and `secretCaptures` on steps, and they read each secret as `{ name, step, set, expiresAt }`, never a value. Output with a secret reads `[secret:<name>]` for them too.
- **Deleting.** When a person marks a runbook done or abandoned, Runbooks deletes its area prefix `runbooks/<id>/`. An agent that closes a runbook has no person to act as, so the secrets are deleted the next time a person with Use secrets opens the Runbooks tab. OpenBao Secrets deletes whatever is left when it expires.
- **Audit.** Runs that read or store a secret are audited with the secret's name only ("read secret api_token", "stored secret api_token"), and so is each deletion. OpenBao Secrets audits each call with the area and the name.
- **Made and asked secrets (1.4.2).** A Make a secret step's value is made on the server only when a signed-in person clicks Make it (never for a Termix API key or an agent token), with `crypto.randomInt` for each character or word, so no character is likelier than another. An Ask for a secret step's value comes from the person's browser once, in that request; it is trimmed and checked against the step's pattern in a separate context with a time limit, and a refusal never repeats the value. Either value goes straight to its store through OpenBao Secrets: Runbooks' own area, the person's or the shared library (create only: a secret that is there is never replaced), or an app path through `createAppField` (create only, never read back, only for paths an OpenBao Secrets admin allows and for people with Create app secrets). The answer, the run row, events, notifications and the audit line ("made secret db_password (32 letters and digits) in the runbook's secrets") carry the name, the format and the store, never the value. Every later run of the runbook reads the made and asked values back as the person who runs it (library and runbook stores only) and hides them in its output like a secret it reads; a person without Use secrets gets no such redaction, and the reads add OpenBao Secrets audit lines.
- **By hand.** Without OpenBao Secrets, or while it is not connected, a secret step shows where to keep the value by hand. Runbooks then has no value at all: the person marks the step done, and a later step that reads the secret does not run.

## VM steps

A VM step (1.4.7) lets a person do one action on one VM through HAW VM Manager's service, `haw.vms`, which Runbooks declares as an optional requirement. Without HAW, or with a HAW older than 1.0.3, VM steps say why they cannot run and nothing else changes.

- **What it lets a person do.** Start, shut down, restart or read one VM that an agent named, or open its console in Remote Desktop: no more than HAW's own tab lets that person do. HAW checks the person's HAW role (viewer to read, operator or owner for anything else), runs its own fixed `vmctl` command over the host's SSH login, and the host's own limits (name pattern, protect list, ceilings) refuse what they refuse. Runbooks sends HAW a VM name and an action, never a command.
- **Agents never act.** A VM step is always a person's (`owner: "agent"` is refused), the button is a person route (refused for agents and Termix API keys), and the agent API has no route that acts. The agent's one VM route, `GET /vms`, answers from a copy: when a signed-in person makes a token or saves its hosts, Runbooks reads HAW as that person, marked as a read for an agent token (HAW answers only its `hosts` and `list` verbs for it), and keeps each host's VM flag, verbs and VM names (with CPUs, memory and whether the host's limits allow actions) in the token's host list, with the time it was read. The copy has no VM state. If HAW is not there or refuses, the token still saves, without VM data. People who manage tokens see the copy, as they see the hosts.
- **Runbooks never acts as someone else (T-032).** It does not ask for `users:impersonate` and never calls `ctx.asUser`; a test fails if backend code does. So an agent request, which has no acting user (a Runbooks token is not a Termix login), never reaches HAW: Termix core refuses any service call without an acting user (`EPLUGINSVCACTOR`), and HAW refuses a caller whose `user` is not the acting user. The copy above is how agents learn VM names; the check that a VM step names a VM host uses it too, and when the copy cannot say, the card checks the host when the person opens it.
- **Force asks on its own.** `force` (turn off, hard reset) is shown in red, and the person confirms it after the usual confirm with a second question; a yes to a repeat, a wait or the order is not a yes to force.
- **The usual questions.** The revision, the order, the wait timer, the `when` rule and the repeat guard (the same action on the same VM in the last 24 hours) apply as for a Run.
- **Who HAW thinks it is.** HAW hands Runbooks a key through a receiver only Runbooks can register (`runbooks.hawVmsKey`), as OpenBao Secrets does; Runbooks keeps it in memory, takes one only while its own request for it runs, and asks again once when HAW refuses it (HAW makes new keys each time it starts). Every call carries the acting person, and HAW refuses a call that names anyone else. An admin must add `runbooks` to HAW's **Plugins that may act for a person**, and can take it off again at any time.
- **What is kept.** The run keeps the action, the VM's details as HAW answered them and HAW's refusals. HAW keeps each action and console in its record with "via runbooks: runbook N step M"; the reads a waiting step makes every 2 seconds are not in HAW's record, but core's audit log has every call.

## Agent notifications

Off until an admin turns them on (see [Agent notifications](notifications.md)).

- **Ids and labels only.** A notification carries the event's id, type and reason, the runbook and step ids, the step's position, the runbook's owner as the agent set it, and a link path. Never output, a command, a value or the text of a note. Agents read those through the agent API with their own token, so hidden output stays hidden.
- **Signed.** Each request has an HMAC-SHA256 signature over a timestamp and the body, with a 32-byte secret that Runbooks makes. The secret is shown to the admin once and kept sealed with Termix's installation key in Runbooks' own table, so delivery can sign without a signed-in person. A new secret replaces the old one at once. The secret is never sent to the browser again, never written to the audit log, and never in an error.
- **Where to.** https only: an `http` address is refused when saved and when sent. Requests go through Termix's outbound guard (`ctx.fetch`): the webhook's own host is the only private address allowed, redirects are refused, each request stops after 10 seconds, and the certificate is always checked, against the admin's CA when one is set.
- **Who.** Only an admin (Manage plugins) can see the settings, make a secret or send a test; a Termix API key cannot. Making a secret and each test are audited.
- **What is kept.** Each event's delivery time, its number of attempts, and the last error in short, with the address's query string left out.

## Markdown

Text from agents renders as Markdown without raw HTML and without images. Links open in a new tab without a referrer.

## Audit

Runbooks writes an audit line for each run, each stop, each start before a wait ended, each send to a terminal, each completion, each step marked done or failed by hand, each agent step an agent ended, each VM step's action and console (1.4.7), each skip, each deletion of a runbook's secrets, and each token made, changed or revoked. Secrets are named, never shown. Termix also records each SSH connection and each host lookup.

## Capabilities

| Capability         | Why                                                                         |
| ------------------ | --------------------------------------------------------------------------- |
| `db:own`           | The runbooks, steps, runs and tokens tables                                 |
| `network:serve`    | The routes under `/plugin-api/runbooks/`                                    |
| `ui:surface`       | The Runbooks tab                                                            |
| `hosts:read`       | Host names, the hosts offered for a token, and access checks                |
| `ssh:connect`      | Run a step over SSH, and read whether a host takes SSH and has a stored key |
| `credentials:use`  | Use the host's stored login for that run                                    |
| `network:outbound` | Send agent notifications to the admin's webhook (1.4.0); nothing else       |
| `secrets:own`      | Seal the notification signing secret with Termix's installation key (1.4.0) |

Runbooks also declares the services `openbao-secrets.store` (`^1.0.0`), for secrets, and `haw.vms` (`^1.0.0`), for VM steps (1.4.7), as optional requirements. They need no capability of their own.
