# Changelog

## 1.4.9 (unreleased)

### Added

- **Send to terminal fills the Mark done box with its own output** (T-249). The person no longer copies the output from the terminal, which a phone cannot do. Once the person presses Enter in the terminal, the **Mark done** box fills with what the command prints, and follows the terminal until the person changes the text. It only fills the box: a line above it always says "Check the text before you save it" (or "The terminal waits for a password"), and it never says the command finished (BUG-021, owner's choice 2026-11-23: guessing where the output ends is what kept failing). **Read again** reads the terminal again and puts its text back after a change. The person still sees, can change, and presses **Mark done** or **Mark failed**. The toast after Send to terminal says the output comes back to the step.
- It reads SSH Terminal's handle on the terminal tab (`readBufferLines`, `subscribeOutput`, `getInputModes`, `isAtPasswordPrompt`), which the plugin SDK does not declare: every part is tested before use and never throws. Without it (a Termix that changes it, plugin API 2's frames, a page reload, another device), the box is the empty paste box it was. The screen is read once, before the command is typed, to note the prompt; the text comes only from the raw output after that (BUG-019, BUG-021), so a reflow, a full scrollback, `clear` or tmux cannot bring another run's text in. The text starts only after the command's echo: the line the shell ends on Enter must be the noted prompt's end with the command (bash 5.1+ draws a pasted command again on Enter, a long or multi-line one after moving the cursor up; that redraw is followed). When the echo is not the command (the person changed it), or cannot be followed, nothing is read and the person pastes. The reading stops at the next prompt (where the shell turns line editing on again, `ESC[?2004h`, which bash 5.1+, zsh and fish send, so a prompt that `cd` changed still ends it; or, for other shells, the prompt noted before the send at the start of a line, if it is 3 characters or more), at a cursor move to another row (`clear`, a progress display, tmux; a note says the end may be missing), at Mark done's size limit (256 K characters) or at the time limit (an hour, or the step's longer one). Lines that look like a prompt (`# ` in a config file, a progress bar ending in `% `) never end it. What the person runs after is never read. While nothing new comes, the box reads every 5 seconds, and it stops reading once the reading stopped. No reading starts when the terminal's last line does not look like a prompt (a tmux status line, a MOTD still printing). A reading stops where it is when another Send to terminal types into the same terminal or its tab closes, and ends when the run is done or failed on another device or reopened; up to 20 are kept. Tests play bash 5.2 output recorded in a terminal (a read before the echo, a changed command, `clear`, a root prompt with `cat` of a config file, a command of two lines, a pause after a progress bar, a command typed ahead after `cd`, a long command redrawn on Enter, a two-line prompt) on the real terminal library (`@xterm/xterm` 6.0.0, a dev dependency).
- A run's `outputSource` says where its pasted output came from: `pasted`, `captured` (from the terminal, as read) or `captured-edited`. `POST /runs/{id}/complete` takes it (default `pasted`; 400 for another value); a run with no pasted output has `null`, as do runs from before. The run shows "Output read from the terminal" or "…, then changed" for it; agents read it on every run, and `null` on a hidden step, since whether it printed anything is its output too (BUG-019). It is what the page reports, not proof that the text was not typed by hand. Captured text is the run's `pastedOutput`, so secret masking, checks, captures and secret captures read it as they read a paste. docs/agent-api.md has a section "Output read from the terminal", and docs/security.md says what is read and what is not (no-echo input never reaches the screen; echoed text is read like any output).
- **Mark failed** sends the text read from the terminal only if the person opened (clicked or tapped into) or changed the box; otherwise it sends no output, as in 1.4.8 (BUG-019, owner's choice 2026-11-23). A line under the buttons says so. **Mark done** is unchanged.
- New column `runs.output_source` (migration 0020), for SQLite, PostgreSQL and MySQL.

### Changed

- The latest run's Mark done box starts empty for each new run; it kept the text typed for the run before.

## 1.4.8

### Fixed

- **A VM step's card no longer shows an old read.** The card read its VM only when it opened and when its own step ran, so a VM that an earlier step made or changed still showed as not found, and the button stayed off until the person found **Read again**. The card now reads the VM again when a run of any step of the runbook ends, and when the page shows again after a minute or more; one read runs at a time. **Read again** is an outline button with an icon next to the VM's state, and the card says how old the read is ("read 3 min ago"). A failed read, or a VM HAW cannot act on now, shows in a box with the time of the read, a line that an earlier step may have made or changed the VM, and **Read again**. The action button stays as it was after a failed read: pressing it asks HAW again.

## 1.4.7

### Added

- **VM steps.** A step's `vm: { host, name, action, force?, waitFor?, waitSeconds?, value? }` gives the person one button, and HAW VM Manager (1.0.3 or later, through its service `haw.vms`) does the action on that VM as the person who pressed it, with HAW's roles and the host's own limits (name pattern, protect list, ceilings). `action` is `start`, `stop`, `restart`, `show` or `console`. HAW keeps each action in its record with "via runbooks: runbook 12 step 3". An admin adds `runbooks` to HAW's **Plugins that may act for a person** first; until then, and without HAW, the step says why it cannot run.
- The step waits for `waitFor` (by default the state the action leads to: `running` for start and restart, `off` for stop; none for show; `null` for no wait), reading the VM every 2 seconds for up to `waitSeconds` (1 to 600, default 300), and fails at the limit with the last state. When HAW restarts or updates during a wait, the step says "HAW VM Manager did not answer; it may be restarting" and goes on to its time limit; Runbooks binds to HAW again only on HAW's code `bad-key`, and steps that wait at once never clear each other's key. Its run, in mode `vm`, shows each state as it changes, and ends with the VM's details as JSON and one summary line ("wyatt-pc-builder is running, 192.0.2.10"), which checks (`contains`, `notContains`, `matches`, `notMatches`) and `when` output rules read. `value: "build"` sets `{{build.state}}`, `{{build.id}}` and, when the VM has an address, `{{build.ip}}` (the first IPv4 address, else the first) and `{{build.addresses}}` for later steps.
- The card shows the host, the VM, its state now (HAW's `show`, read when the card opens, `GET /steps/{id}/vm`), what the action does and how long it waits, and "the host refuses this" for a protected VM's stop or restart and for a VM outside the host's name pattern. The button names the action: **Start VM**, **Shut down VM**, **Restart VM**, **Show VM**, **Open console**; with `force`, **Turn off VM** or **Reset VM** in red, with a question of its own (409 `force`, then `confirmForce: true`). `POST /steps/{id}/vm` keeps the usual questions: the revision, the order, the wait timer, the `when` rule and the repeat guard (the same action on the same VM in the last 24 hours; not for show and console). Two steps with the same power action on the same VM, pressed at once, do not both pass it: the second gets 409 `running` until the first run is written, and then 409 `repeat`. A host whose verbs HAW has not read yet refuses every action (409 `verbs-unknown`). A host's refusal fails the step with HAW's words; HAW's own refusals (Runbooks not allowed, the person's HAW role, a host HAW does not manage or whose `vmctl` does not offer the verb) refuse the button with 403, 404 or 409 and run nothing. **Stop** ends a wait.
- **Open console** opens the VM's console host in a Remote Desktop tab, as HAW's own tab does, and the step waits for the person's **Done** or **Failed** (`POST /steps/{id}/vm/end`). Its run keeps one summary line, not HAW's console details (the console's address and the VM's id).
- A new step kind, **VM action** (indigo, Server), with its own color setting.
- Agents: `vm` on create, add, change and amend, through REST and MCP, and in `get_runbook`. A VM step has no `hostId`, `command`, `captures`, `secretCaptures`, `stdin`, `timeoutMs` or `interactive` and cannot be an agent step (400); `force` is for stop and restart only; `host` must be one of the token's hosts and, when HAW can say, one HAW manages. `GET /vms` and the MCP tool `list_vms` answer the token's VM hosts and the VMs on one from a copy Runbooks reads from HAW, as the signed-in person and marked for an agent, when that person makes the token or saves its hosts; the copy has the time it was read and no VM state, and a token saves without it when HAW is not there or refuses. An agent request never reaches HAW (it has no acting user), and Runbooks never acts as another user: it does not ask for `users:impersonate`. Agents never act on a VM. `hideOutputFromAgents` works on a VM step, and the built agent view test has a VM case and one that changes only the state. A hidden VM step's `{{build.state}}` is one of a few words, so it is not masked in other text (nor is a Decision's option id): whether "running" came back masked would tell the state. A step whose command, checks or standard input reads such a value is hidden from agents instead, and so are the values it captures and the steps that read those. The agent API doc has a section "VM steps"; docs/security.md says what a VM step lets a person do.
- New column `steps.vm` (migration 0019), for SQLite, PostgreSQL and MySQL. The manifest declares `haw.vms` (`^1.0.0`) as an optional requirement.

### Fixed

- **Interactive steps on Windows hosts.** Windows (ConPTY) paints every row of the terminal empty before the first text, so an interactive run's output started with 39 empty lines; the output now drops empty lines before the first text, in the live output and in the stored output alike. This holds for every host's terminal output, Linux too: an interactive run on Linux no longer starts with the empty lines a program printed first. The agent API doc's "Typed input" says that under a terminal a Windows host may report exit code 0 (wyatt-pc did for `exit 7`), so such a step checks its output instead of its exit code, and that **End input** (Ctrl-D) may not end the input there. How Runbooks reads the exit code does not change: Linux hosts give real exit codes under a terminal.

## 1.4.6

### Added

- **Run or Send to terminal.** A step's `runIn` says how the person may start its command: `"either"` (the default, as before), `"terminal"` (Send to terminal only) or `"run"` (Run only), with an optional one-line `runInReason`. The step card shows only the button the step allows, with a line that says why ("Send to terminal only: it opens your browser."), and a terminal-only step's chip says "Terminal on <host>" instead of "Run on <host>". The server refuses Run on a terminal-only step with 409 `terminal-only` and Send to terminal on a Run-only step with 409 `run-only`, before it asks about the order, the wait or a repeat; the answer carries `reason`.
- `runIn` and `runInReason` work when an agent creates a runbook, adds, changes or amends a step, through REST and MCP, and show in `get_runbook`. Only a step Termix runs on a host may set them (400 otherwise), and `"terminal"` cannot have `stdin` (400). Older steps read as `"either"`. The agent API doc has a section "Run or Send to terminal".
- **Conditional steps.** A step's `when` rule says when it is needed, from earlier steps only: how a step ended (`{ "step": 8, "status": "failed" }`, also `done`, `skipped`, `ran` and `not-needed`), what its latest run printed (`{ "step": 1, "output": <any check> }`, with `{{name}}` values and secrets hidden), what a decision step chose (`{ "step": 5, "chose": "rollback" }`), or a value (`{ "value": "mode", "equals": "fast" }` or `matches`), combined with `all`, `any` and `not` (at most 4 levels and 20 rules). Steps are written as `3` or `"3a"`, as in `stdin`. A rule that names this step, a later step, a capture the step does not have, or an option a decision does not have is refused with 400. It works when an agent creates a runbook, adds, changes or amends a step, through REST and MCP.
- Runbooks works out each rule's state every time it reads the runbook (`waiting`, `met` or `not-met`) and never stores it, so reopening an earlier step changes the answer. Each step has `condition: { state, rule, reason, notNeeded }`; the reason never quotes output. A pending step that never ran and whose rule does not hold is **not needed**: it counts as ended for the order of later steps, the next step, the bar and the rail, the progress (`notNeeded`, and "2/5 done · 1 not needed"), the list's next kind and `agent-turn`. A step that ran keeps its result. A step that is not needed is not "the step before" for a wait timer: `waitAfterPreviousSeconds` counts from the last step before it that ended.
- A rule reads the author's values and what steps **before** it captured, also for `{{name}}` in an output rule, so a later step that captures the same name cannot change it. A rule that names a step an amendment replaced reads its latest replacement. An output rule on a decision step reads the chosen ids, one per line; a decision that is skipped, or reopened and not chosen again, has no output, no `value` and matches no `chose` rule. A step a rule names cannot be removed (409 `when`) or moved after the rule (400). A change to a step's `captures`, `decision` or `interactive`, and an amendment that replaces a step, check again every rule that reads the step and answer 409 `when` when one no longer fits.
- **A rule never reads hidden output.** Every rule, whoever wrote it, is worked out on what the agent view shows: a hidden step's output and captures read `[hidden by owner]`, a hidden value is masked in other steps' output and captures, and `{{name}}` is filled with the masked value. So a rule's state, `nextStepId`, the progress, `agent-turn` and an agent's 409s are the same whatever the hidden values are. To branch on hidden output, give the hidden step a check and the later step a status rule; on the page, a rule that reads hidden output says "This rule can't see hidden output". An agent's rule that reads a hidden step's output, a value such a step captures, or such a value as `{{name}}` is refused with 400 as an early error.
- Rules are cheap to read. What a pattern said of a finished run or a value is kept for the server's life (1000 answers for each of the 50 runbooks read last), so a page load or a list poll tests no pattern twice. The patterns of one read, or of one list of runbooks, share a limit of 500 ms; a rule whose pattern that limit stopped is `waiting` ("not worked out yet") until a later read, and no `agent-turn` is sent while the turn is not known.
- On the page, a step that is not needed is one grey line in its place, "3 · Way back — not needed: step 1 is done and step 2 is done"; a click opens it. A step whose rule still waits says "Only if step 1 failed or step 2 failed". **Hide not needed** leaves them out of the cards, the rail and the bar, and the browser remembers it.
- A person can still start a step that is not needed: Run, Send to terminal, Make it or Save and Done or Failed answer 409 `not-needed` with the rule and the reason, the page asks **Run anyway?**, and a start after a yes (`conditionAnyway: true`) is in the audit log, written only once every other question passed. An agent cannot complete its own step when it is not needed (409 `not-needed`). The agent API doc has a section "Conditional steps", and its events section says how `agent-turn` treats a step that is not needed.
- **Decision steps.** A step with `decision: { options, multiple?, min?, max?, value? }` lets the person choose from 2 to 10 options the author wrote (`id`, one-line `label`, optional short Markdown `description`), with radio cards or, with `multiple`, check boxes from `min` to `max`. There is no free text. **Confirm** (`POST /steps/{id}/decide`) ends the step done with a run in mode `decision` whose output is the chosen ids, one per line, and sets `value`, when given, to the ids joined with commas. The card then says "You chose: Go back to the old release", by whom and when. A decision step has no host, command, checks, captures, stdin or wait timer, cannot be hidden from agents (400; the page offers no Hide on it), and only a person decides (`owner: "agent"` is refused).
- **Reopen** on a decision lets the person choose again. When steps that read it already ran, the page names them first ("Choose again?"); they stay as history, and steps that have not run follow the new choice (`decisionRan` on the step).
- The agent view shows `decision` and `choice`; `step-done` carries "chose <ids>" as its note. A new step kind, **Decide** (amber, Split), with its own color setting. The agent API doc has a section "Decision steps".
- **Typed input.** While a Run runs, the person who started it can type into the command from the runbook page: a line under the live output, "Type into the command", with **Send** (Enter), **End input** and an eye to hide what they type. It shows on every Run without `stdin` and shows the time left of the step's limit. It lights up and starts hidden when the last line of the output looks like a prompt for a password, passphrase, token or PIN. Another person sees who can type instead. On a phone, Send and End input wrap under the field.
- `POST /runs/{id}/input` with `{ text, hidden?, end? }` writes to the command's standard input. Only the person who started the run (403 `not-your-run`); never a Termix API key or an agent. 409 `not-running`, `stdin-source` (the run got `stdin`) and `input-closed` (input ended); at most 4 KB at once (400 `too-long`). End input is EOF, or Ctrl-D for an interactive step: twice in mid-line, so the line goes to the command as typed, without a line end added. On an interactive step, Send ends the line with CR, as a terminal's Enter does (PowerShell's `Read-Host` under Windows OpenSSH may not take LF), and a line sent with LF gets CR; other Runs keep LF. Ctrl-D is the Linux and Unix end of input and may not end input on a Windows host.
- What the person types is never stored or logged. The run keeps `inputs: [{ at, chars, hidden, ended }]`, the audit line `runbooks_step_input` says "input sent: 14 characters, hidden", and agents see only `inputCount`. How many characters were typed (`chars`) shows only to the person who typed; others get `null`. A hidden text of 4 characters or more is replaced with `[secret:typed]` in the live output, the stored output and what the checks read; on an interactive step, so is its copy as the terminal shows it, with control characters taken out.
- **Interactive steps.** `interactive: true` makes Run open a terminal (pty) for the command, so `sudo`, `ssh` and `ansible --ask-become-pass` can ask for a password. Its stdout and stderr come as one stream; line ends, colour codes and title codes are taken out before the output is shown, kept or checked. It cannot have `stdin`, `secretCaptures`, a check or an output rule on `stream: "stderr"` or `runIn: "terminal"` (400), and only a step Termix runs on a host may set it. The step's chip says "Interactive". It works through REST and MCP and shows in `get_runbook`. The agent API doc has a section "Typed input".
- The Run confirm shows each capture's and secret capture's pattern under the checks, so the person sees all that reads the output before it runs.
- New columns, added for SQLite, PostgreSQL and MySQL: `run_in` and `run_in_reason` (migration 0014), `when_json` (0015), `decision` (0016), `steps.interactive` and `runs.inputs_json` (0017), and `runs.error_parts_json` (0018). Steps and runs from before read as they did.

### Changed

- **The agent view is built, not masked.** Nothing an agent reads depends on a hidden value: a test builds each of 14 runbooks twice, with two hidden values, and compares all that agents read through REST, MCP, events, the list and webhooks. A run's `command` and its check results' words are filled from the step with the values agents saw when it ran, so a literal an agent wrote stays as written. An agent's own output and command, and a decision's choice and value, are never masked. Agents see a visible step's captured value masked when it holds a hidden value, in its run and in `effectiveValues`.
- An agent step's checks are tested with the values agents see, and a check there that uses a hidden step's value is refused (400 on create, add, change and amend). A step whose `stdin` is a hidden step's output or a hidden value counts as hidden. A hidden step that ended done shows each capture it declares as `[hidden by owner]`, matched or not, also in a later step's `missing`; it shows `truncated: false`, no `lastOutputAt`, and a failed check on it says only that it failed. A hidden step's run, and a run that read a secret, show agents no `stdin.bytes`.
- A run's `error` for agents is built from its parts. A hidden step's failed run says `[hidden by owner]` and its run that ended done says nothing, so agents do not learn that a capture pattern took too long on the hidden output, or which secret capture found no match. On a visible step only Termix's own words are masked: a capture or secret name that equals a hidden value stays as written. A run from before 1.4.6 keeps its masked text.
- docs/security.md says what stays possible: a visible step that a person runs can print a hidden value in a changed form, or one shorter than four characters; and a hidden step still shows agents its status, exit code, check results, run time and whether its secret captures matched.
- Live output that hides secrets holds back only an end of the output that a hidden value starts with. It held back the last characters (as many as the longest value, less one) of each stream before, so a prompt such as "Password: " showed only when more output came. When one value holds another, it holds back from where the longer one may start, so no part of it shows.

### Fixed

- Checks fill `{{name}}` values, with the same values as the command (the author's, then captures). A check `contains "registry:5443/app:{{ver}}@sha256:"` looked for the text `{{ver}}` and always failed. `text` in `contains` and `notContains` and `equals` in a `value` check get the value as it is; a pattern (`matches`, `notMatches`, `matches` in a `value` check) gets it as literal text, escaped, so a value `1.2.3` matches only `1.2.3`. The step card and the Run confirm show the checks filled in (`resolvedChecks` on each step), and the run's results name the filled text.
- A check whose value is not set stops the step, as a command's does: the step's `missing` names it, and Run, Send to terminal, Mark done, Done on a step run outside Termix and an agent's `complete_step` with `done` answer 409 `missing-values`. Mark done and `complete_step` test the checks with the values the runbook has at that time.
- When a check uses a value, the hash the person approves (`commandHash`) covers the checks with their values, so a value that changes between the Run confirm and the run answers 409 `stale`. The run keeps the command's own hash, so "the same command ran on this host" still means the same command, whatever its checks.
- An agent never sees a value from a step hidden from agents in a check result: the result's label and detail are built from the step's check filled with `[hidden by owner]` in its place, also where a pattern holds the value escaped.
- Captures read the output with its secrets hidden, as checks do: a capture took part of a secret from the output before.
- An agent's create or add-steps that is refused stores nothing. Every step is checked before the first is stored, through REST and MCP. Before, a bad `stdin` in a later step answered 400 but left the new runbook, or the steps before the bad one, in the store.
- The agent API doc ("Checks", "Values") and the MCP tool help say that checks take values.

## 1.4.5

### Fixed

- The MCP tool schemas told agents a library secret path the server refuses (`mine/a/b/c/d/e`, or one with an empty part). Their library, app field and name patterns now come from the regular expressions the server checks with, and a test keeps them equal.
- The agent API refuses a body that is not an object with 400 "body must be an object" when it creates or changes a runbook, adds steps or reorders them. An array was taken as an empty body before, and adding or reordering steps with no body said only that steps or stepIds were missing.
- The wait timer of a Make a secret or Ask for a secret step had no test. A test now checks that an early Make it gets the 409 `wait` answer, and that `waitAnyway` makes the secret.
- Copy in the boxes that show a new agent token or the notification signing secret once says "Copied" after a copy, as every other Copy button does.
- A refused **Mark done** with pasted output, or a refused note save, reads the runbook again, as a refused **Stop** already did, so the page does not show a step that changed meanwhile.
- The agent tokens page shows the server's error text only when it is text, and its general message otherwise, instead of turning any error value into text.
- "Stored until" on a secret step uses the same time format as the rest of the page; a value that is not a date shows as it was sent instead of "Invalid Date".

### Changed

- The release and CI workflows follow the current Termix plugin template: write permissions only on the release job, only the two secrets it uses (`TERMIX_PAT`, `TERMIX_PLUGIN_SIGNING_KEY`) instead of every secret, and no `overwrite` mode. Dependabot updates npm packages (not the plugin SDK) and the pinned actions weekly.
- The frontend tests share `tests/frontend/helpers.tsx`: the rendered app, typed builders for what the server sends (`makeSummary`, `makeStep`, `clickStep`, `makeRun`, `makeRunbook`), a fake of the routes (`fakeApi`), `openRunbook`, `card` and `flush`. Their fixtures now match the server: a wait names the previous step's `label`, the fake `GET /runbooks` sends the list fields only, and `GET /colors` sends no colors.
- The backend tests share `useTestServer`, `setupRunbook` and `execResult` from `tests/backend/helpers.ts`, instead of a copy of each in every file.
- The tests of `src/shared` code (values in text, SSH hosts, step numbers) moved to `tests/backend/shared/`.
- `{{name}}` in a command is filled by `fillPlain` in `src/shared/fill.ts`, the filler of a step's `where`, instead of a copy in `src/backend/values.ts`. A new test pins the resolved text and hash of a set of commands, and they did not change. The agent view's `missing` comes from the same fill instead of a second scan of the command.
- The rules on names live in `src/shared/names.ts`: the value and secret name (`NAME`, which was `VALUE_NAME` and `SECRET_NAME`), `{{name}}` (`PLACEHOLDER`), `MAX_SECRET_NAME`, `LIBRARY_REF`, `secretNameProblem`, `regexProblem` (the check on a capture, check or ask pattern) and `isOneLine`. The server's checks, the MCP schemas and the page's store line use them instead of their own copies; every error message is the same.
- A step's `body`, `expect` and `where` are filled by one function, `fillStepText` in `src/shared/fill.ts`: the server's `resolvedBody`, `resolvedExpect`, `resolvedWhere` and `textMissing` come from it, and the page uses it with its "not set yet" marker instead of its own copy. The API sends the same fields as before.
- What the person routes send is typed once, in `src/shared/api.ts`: runbooks, steps, runs, waits, inputs, secret states, amendments, progress, tokens and the 409 answers the page asks about (`ConflictBody`). The server's view builders (`personView`, `runbookSummary`, `amendmentView`, `progress`, `runSummary`, the runbook list) return these types, and `src/frontend/api-types.ts` re-exports them instead of a hand copy, so the server and the page type-check against one definition. Fields the server always sends are required, and the page no longer falls back from `agentLabel` to `createdBy` or from a step's `label` to its position. `Translate` has one definition.
- Small rules have one definition each. The page numbers steps and matches a step's secrets with `stepLabel` and `stepRef` from `src/shared/steps.ts`, as the server does. `isAgentStep` and `isOutsideStep` there tell the step kinds, the step card, the person view and the routes which steps Termix never runs. `MAX_SENT_NOTE` lives in `src/shared/limits.ts`, and `secretLabel` (the name of the secret a step's input reads) in `src/shared/names.ts`.
- One module (`gates.ts`) decides whether a step may be acted on: an agent step, a closed runbook, a replaced step, a stale page, missing values, the order and the wait timer. Run, Send to terminal, Done and Failed, secret steps and an agent's completion all use it, each asking in its own order. Send to terminal no longer asks about an agent step twice.
- `events.endStep` ends a step everywhere, including the sweep at start-up. `judgeOutput` finds secrets, hides them, takes captures and only then runs checks, so checks still never see a secret.
- `insertRun` fills in the fields that an unfinished or hand-ended run does not have. `events.changeRunbook`, `secrets.read`, `storedRun`, the audit helpers and one `APP_STORE_NEEDS` replace copies that were in two or three places.
- `http.ts` (wrap, idParam, body, requireSignedIn, refuseApiKey) and `parse.ts` (InputError, strictObject, optionalText, parseOutcome) are shared by the person, agent and admin routes. Each keeps its own wording.
- The store reads rows by id, nullable columns, query conditions and JSON patches through one helper each.
- The page's text helpers (times, durations, sizes, waits, the input source, the host label, the run summary) live in `format.ts`, and its clocks (`useTick`, `useFetchedAt`, `useWaitRemaining`, `usePolling`) in `timers.ts`.

## 1.4.2

### Added

- **Make a secret** steps. A step with `generate: { name, format, length, store }` makes a new random value on the server when a person clicks **Make it**: `alnum` (letters and digits, the default, 16 to 128, default 32), `hex` (16 to 128, default 64), `base64url` (16 to 128, default 43), `words` (4 to 12 words of the EFF long word list joined by `-`, default 6) or `pin` (4 to 12 digits, default 6). Each character or word is picked with `crypto.randomInt`, so there is no modulo bias. The step says "Make secret <name>: 32 letters and digits" and where the value goes.
- **Ask for a secret** steps. A step with `ask: { name, label, pattern?, store }` takes a value the person types or pastes once, such as a token another site shows, in a field that shows it while it is typed with **Hide** (as in OpenBao Secrets 1.0.2), then **Save**. The value is trimmed and must match `pattern` whole (checked with a time limit); a refusal never repeats it.
- Where the value goes, `store`: `"runbook"` (the default: the runbook's own secrets, as captured ones, for 7 days and deleted when the runbook ends), `{ library: "mine/<path>" | "shared/<path>", expires?: <days, 1 to 30> }` (a new secret in the OpenBao Secrets library, never replacing one: 409 `exists`), or `{ app: "<app>/<host>", field }` (a new field through OpenBao Secrets 1.0.5's `createAppField`, for app paths its admin allows; 409 `app-store-off`, `app-not-allowed` or `exists` when it refuses).
- The value never reaches the browser, an agent, an event, a notification, the audit log or any output. The run (`mode: "secret"`) says "Made secret <name>" or "Saved secret <name>" with `secrets.made` (`name`, `how`, `store`, `where`, `expiresAt`). Later steps read it with `stdin: { from: "secret", name }` (or the library form), and every later output of the runbook shows `[secret:<name>]` instead of it, also in steps that do not read it.
- By hand: when OpenBao Secrets is not installed or not connected, or an app path store meets an OpenBao Secrets without `createAppField`, the step shows **Do it by hand**: for Make a secret the format and length to make in a password manager, then the KV engine, path and field to save it at in OpenBao or Vault (each with Copy), and **Done** and **Failed**. A later step that reads the secret says where to get it.
- `POST /plugin-api/runbooks/steps/{id}/secret` (`{ revision, value?, confirmRepeat?, outOfOrder?, waitAnyway? }`), a person only, asks about a repeat, the order and a wait as Run does. Agents can set `generate` and `ask` (REST, MCP, amendments) but never make, save or complete such a step; `owner: "agent"`, a command, a host, `where`, `stdin`, captures, secret captures and checks are refused on it (400), as are bad formats, lengths, names, labels, patterns and stores.
- Two step kinds in the registry: **Make a secret** (fuchsia, Dices) and **Ask for a secret** (teal, Clipboard paste), with their own color settings.
- The EFF long word list (CC BY 3.0 US), credited in NOTICE and the README.

### Changed

- A step that reads a secret by name may read one an earlier step made or asked for with store `"runbook"`. Reading a library or app store secret by name is refused with a hint to use the library form.

## 1.4.0

This update asks the admin to agree to two new capabilities: `network:outbound`, to send agent notifications to the webhook an admin sets, and `secrets:own`, to keep the webhook's signing secret sealed with Termix's installation key. Runbooks sends nothing until an admin turns notifications on.

### Added

- A runbook's owner. Agents set `owner: { task, agent, label }` on a runbook (create, `PATCH`, `create_runbook`, `update_runbook`): a task id (up to 64 characters), an address of the agent's session that a notification receiver understands (up to 200), and a label for the person (up to 80). The person sees "Agent: <label or token name> · task <task>" under the title.
- Agent steps. A step with `owner: "agent"` is work the agent does itself. The person sees "Waiting for the agent" with the agent's label and can only Skip or Reopen it; Run, Send to terminal and Done are refused with 409 `agent-step`. Its command, if any, is shown as "What the agent will run" and needs no host. Captures, secret captures, standard input, wait timers and `exitCode` checks are refused on it (400).
- `POST /agent/steps/{id}/complete` (MCP `complete_step`): `{ outcome: "done" | "failed", note?, output? }` (note up to 2000 characters, output up to 64 KB). Only for an agent step, once every earlier step ended; refused with 403 `person-step`, 409 `order`, 409 `ended` and 409 `closed`. It records a run in mode `agent` with the token's name, the note and the output, which the step's checks test. Audited.
- Events: `agent-turn` (an agent step became the next step), `step-failed` (with `reason` `exit`, `check`, `stopped`, `interrupted`, `secret` or `manual`), `runbook-done` (`done` or `abandoned`), `sent` and `step-done` (only when the runbook's `notify` lists it). `GET /agent/runbooks/{id}` lists the latest 100 as `events`; `GET /agent/events?since=<id>&limit=<n>` (MCP `list_events`) pages through all of the token's.
- `notify` on a runbook: the event types the webhook delivers for it, default `agent-turn`, `step-failed`, `runbook-done`, `sent`.
- Agent notifications, off by default. Admin settings **Notify agents**, **Webhook address** (https only; http is refused) and **CA certificate (PEM)**, and a section with **Make a new signing secret** (32 random bytes, shown once, sealed) and **Test**. Each wanted event is POSTed once as JSON with ids and labels only (never output, a command or a note's text), with `X-Runbooks-Event` and `X-Runbooks-Signature: t=<unix>,v1=<HMAC-SHA256 of "<t>.<body>">`. Retries after 1, 5, 30 and 120 minutes, then it is given up. See [docs/notifications.md](docs/notifications.md), with a receiver that checks the signature.
- Amendments. `POST /agent/steps/{id}/amend` (MCP `amend_step`): `{ kind: "replace" | "substep", reason, step }`. A fixed version (`replace`) of a step that did not end done, or an extra step (`substep`) after a step in any state, goes right after it as **3a**, **3b**: the new step keeps the step's position with a letter (`suffix`), and later steps keep their numbers. A replaced step gets status `replaced`, folds to "Replaced by 3a" with its runs, counts as ended and does not run, take a mark or a skip. The new step says "Amended by <token name>: <reason>" (reason up to 500 characters), and a fixed version shows the old command struck through. An amendment can be amended. Refused with 409 `closed`, `running`, `done` (replace on a done step) and `replaced`, and checked like a new step. A step's output hidden from agents stays hidden in its fixed version. Steps have `label`, `suffix`, `amendment` and `replacedBy`; the runbook list says "amended" while an amendment has not run (`amendedPending`).
- Steps run outside Termix. A person step may have `command` and `where` (up to 80 characters, such as "Windows PC, PowerShell as admin") and no `hostId`. It shows "Run outside Termix: <where>", the resolved command and Copy (off while a value is missing), and no Run or Send to terminal (409 `outside`). The person pastes the output and marks it Done or Failed (`POST /steps/{id}/manual` with `output` and `revision`); checks and captures read the pasted output, and the run has `mode: "outside"`. `where` without a command, with a host, `stdin`, `secretCaptures` or `exitCode` checks is refused (400). Agent API, MCP and amendments take `where`.
- A Copy button on every fenced code block in a step's text and its "You should see" text.
- `stdin` names an amendment as `"3a"`; numbers still name steps.
- Event `amended` (reason `replace` or `substep`, `stepId` the new step), delivered only when `notify` lists it. Events and webhook requests carry `stepLabel` besides `stepPosition`.
- **Send to agent** on every step when notifications are on and the runbook has an owner: "Send step N to <agent>?" with an optional note of up to 500 characters. It records a `sent` event, always delivered, says "Sent to <agent>", and shows in the step's history.

### Changed

- A step with a command and no host is refused with "a step with a command needs a hostId, or where for a command the person runs outside Termix".

## 1.2.0

### Added

- Standard input for a step. Agents set `stdin` on a step: the standard output or standard error of an earlier step's latest finished run (`{ "from": "step", "step": 2, "stream": "stdout" }`, with `allowFailed` to take a failed run's output), a value (`{ "from": "value", "name": "build_id" }`, with one newline), or a secret (`{ "from": "secret", "name": "api_token" }` captured earlier in the runbook, or `{ "from": "secret", "library": "shared/<name>" }` and `mine/<name>` from the OpenBao Secrets library, read as the person who runs it). The step and the Run confirm say where it comes from ("Standard input: output of step 3 (stdout, 1.2 KB)"), with the first 200 characters of a step or value input and never a secret. The approved hash covers the source. Send to terminal is off for such a step. A Run is refused with 409 `stdin-missing` while the input is not there yet.
- Secret captures. Agents set `secretCaptures` on a step (at most 10, the same pattern rules as captures). When its run, or a terminal Mark done, ends done, each match is stored in OpenBao through the OpenBao Secrets plugin, in Runbooks' own area, for 7 days; a pattern that matches nothing fails the step with "secret <name>: no match". A later step reads it as standard input. Secrets never appear in commands.
- Secret values a step captures or reads are replaced by `[secret:<name>]` in its standard output, standard error, pasted output and captured values before anything is stored or shown, also when a value is split across two pieces of live output. The output of a step that captures a secret shows when its run ends.
- A runbook's secrets are deleted when a person marks it done or abandoned, or on the next read by a person after an agent closed it; the rest expire after 7 days.
- Agents read secrets as `{ name, step, set, expiresAt }` on the runbook, and each run's `stdin` (source and size) and `secrets` (names read and stored), in the agent API and MCP. The MCP tools explain `stdin` and `secretCaptures` with an example.
- The OpenBao Secrets service (`openbao-secrets.store` `^1.0.0`) is an optional requirement. Without it, steps that use secrets are refused with "Install and connect the OpenBao Secrets plugin to use secrets"; people who run them need its Use secrets permission.
- Done and Failed buttons for a step with no command, the size of Run. A click records a run in mode `manual` with who, when, the outcome and the step's note; agents see it like other runs.
- Runs keep `startedEarlySeconds` when a person started before the step's wait timer ended; the run history shows "started 36 s early" and agents see the field.

### Changed

- Skip is a separate small button on every pending step, always labelled Skip. "Mark read" is gone: use Done.
- Mark done on a terminal run needs at least one line of pasted output; the server refuses an empty paste with 400.
- An early start on a wait timer asks one question, "The wait is not over: m:ss left (reason)", with the command, Cancel focused and Start anyway as a warning, instead of a Run confirm and then a second question.
